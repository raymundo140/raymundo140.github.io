## Overview

For a John Deere-sponsored embedded-systems challenge at Tecnológico de Monterrey, I built an end-to-end tractor control and telemetry prototype around an STM32 and Raspberry Pi. The STM32 handled time-sensitive embedded functions — input acquisition, the transmission model, UART communication, and local outputs — while the Raspberry Pi handled telemetry, CSV logging, visualization, and operator interaction. I worked across the complete project: embedded architecture, STM32 firmware, Raspberry Pi software, serial communication, the telemetry pipeline, the graphical interface, performance optimization, and integration.

## STM32 Embedded Controller

The STM32 firmware, written in C/C++ in STM32CubeIDE, is organized into five periodic tasks — matrix-keypad input, ADC acquisition, transmission-model execution, UART communication, and LCD output — scheduled as a real-time task set so input sampling, model execution, serial communication, and display updates coexist predictably. The transmission model tracks throttle, engine speed, vehicle speed, and gear, forming the main telemetry stream.

## Bidirectional UART

UART is a true two-way interface, not a one-directional telemetry link. The STM32 streams vehicle-state telemetry to the Raspberry Pi; in the opposite direction, a Tkinter interface on the Pi can send a software-generated throttle value that the STM32 uses as the model input instead of the physical potentiometer once simulation mode is enabled through the keypad.

## Raspberry Pi Telemetry & the Performance Bottleneck

The Raspberry Pi, running Python on Raspberry Pi OS, parses incoming telemetry, logs it to CSV, and plots it live. The first implementation coupled serial reading, CSV logging, and Matplotlib updates in the same execution path, which caused blocking and slower visualization. I reorganized the software so acquisition, storage, and plotting run independently using Python threading and a shared queue, reducing the plotting interval from 200 ms to 50 ms for a substantially more responsive display.

## Operator Interface & Two Operating Modes

A Tkinter throttle slider lets the operator drive the simulated tractor directly from the Raspberry Pi. The system supports two modes: physical-input mode, where the STM32 reads the ADC and feeds the physical throttle into the model, and simulation mode, where the Tkinter slider's value is sent over UART and used as the model input instead.

## Result

The completed prototype, integrated into a 3D-printed physical tractor, connected real-time STM32 firmware and Linux-based Raspberry Pi software into one bidirectional embedded-to-Linux control and telemetry pipeline — streaming throttle, engine speed, vehicle speed, and gear over UART, logging to CSV, and supporting both physical and software-controlled throttle input.
